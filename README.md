# Как проверить LLM-судью на правильных и ошибочных ответах

Самостоятельный пример XNova содержит два набора с независимыми эталонами. В диагностическом наборе — 18 коротких заданий по Python, арифметике и HTTP, 144 парных решения. В сложном — 24 задания по Python, SQLite, закрытым документам, недостающим сведениям и проверке недоказанных медицинских утверждений, 192 парных решения и 24 отдельных свободных ответа. В сохранённых журналах GPT-5.6 Terra выбрала правильный кандидат во всех 144 и 192 парных предъявлениях. Все 24 свободных вывода согласуются с эталоном; два нарушают JSON-контракт по типу поля `answer`. Эти результаты относятся к фиксированным задачам, а не к произвольным запросам пользователей.

Основной код использует стандартную библиотеку Python 3.12; для тестов нужен `pytest==9.1.1` из `requirements-dev.txt`. Все данные заданий синтетические; ключи доступа и адрес сервиса в репозитории отсутствуют. Диагностическая матрица разделена между `examples/experiment_cases.py`, `experiment_matrix.py` и `experiment_analysis.py`. Сложная матрица, оракулы и её офлайн-анализатор находятся в `stress/`. Сетевые клиенты в обоих каталогах отделены от офлайн-команд.

## Проверить диагностический набор

Из корня проекта выполните:

```bash
python -m pip install -r requirements-dev.txt
python -I examples/eval_harness.py --self-test
python -I examples/check_suite.py
python -I examples/eval_harness.py --analyze-recorded data/judge-run-gpt-5.6-terra-2026-10-22.jsonl
```

На Windows при необходимости используйте `py -3.12` вместо `python`. Первые две команды проверяют генерацию матрицы и обработку ошибочных записей. Третья проверяет все 144 сохранённых предъявления, точный текст каждого запроса и версию rubric, затем пересчитывает результат:

```text
attempts=144; valid=144; wrong_wins=0; ties=0
invalid_output=0; refusals=0; timeouts=0; api_errors=0
position_flips=0/72; repeat_disagreements=0/72
```

Фактический вывод — один JSON-объект с этими и групповыми полями. `examples/eval_harness.py` без аргументов печатает **искусственный контроль** `control_wrong_wins=3/4` и `control_order_flips=1/2`; он проверяет анализатор и не относится к модели. Полный журнал имеет SHA-256 `d8262a5481f66f0e92730bfc301951b4465d06ecdc178507d1b11521518221e4`.

## Проверить сложный набор

Из корня проекта выполните:

```bash
python -I stress/v2_harness.py --audit
python -I stress/v2_harness.py --self-test
python -m pytest -q stress/test_v2.py
python -I stress/v2_harness.py --analyze-recorded data/stress-v3-judge-gpt-5.6-terra-2026-10-22.jsonl
python -I stress/generation_audit.py data/stress-v3-generation-gpt-5.6-terra-2026-10-22.jsonl
```

Первые три команды проверяют 24 case ID, десять исполняемых Python/SQLite-оракулов и отрицательные контроли анализатора без сети. Четвёртая отвергает неполную матрицу, дубли, несовпадения prompt и dataset SHA, смешение model ID и некорректные verdict. Для 192 сохранённых оценок её результат: `correct_wins=192`, `wrong_wins=0`, `ties=0`, `invalid_output=0`, `position_flips=0/96`, `repeat_disagreements=0/96`. Пятая команда проверяет структуру 24 ответов: 22 соответствуют JSON-схеме, два имеют неверный тип поля `answer`. Она **не** определяет фактическую правильность свободного текста.

У задачи `sql-01` две позиции заказа соединяются с двумя отгрузками: четыре строки дают `SUM=2000`. Для `sql-03` модель правильно назвала одну строку `(1, 2)`, но вернула JSON-массив вместо строки; для `sql-04` правильно назвала `1`, но вернула JSON-число. Эталон проверен исполнением кода и SQL либо чтением полного синтетического условия; для двух медицинских вопросов утверждения сверены с [NCI](https://www.cancer.gov/about-cancer/treatment/cam) и [NCCIH](https://www.nccih.nih.gov/health/cancer-and-complementary-health-approaches-what-you-need-to-know). Не используйте эти кейсы как медицинские советы.

Сырые журналы имеют SHA-256 `08b320530d6452c006e60d9565063ce0473517df80507fb780e6c12b7d2865c7` для судьи и `26229e584049b430d74be9e390d36d42cd978c6594607b20c2e72271af896426` для генерации. Замороженный датасет: `be8e9d1cff3204d74c2ccf3354b02f8941babb6be7f3b6f224fcd2821d850fa9`. `stress/v2_harness.py --emit-requests` воспроизводит 192 отправленных текста; его stdout имеет SHA-256 `36640539a7d897d2cfd318af8fb2a3158e047387592b3fe16c93f3997cade771`.

## Как устроен опыт

`examples/judge_prompt.txt` и `stress/judge_prompt_v2.txt` задают две фиксированные рубрики фактической правильности. Матрицы детерминированно перемешаны с seed `20261021` и `20261022`. Судье передавались только задача и ответы A/B; в запросе нет метки правильности, case ID или порядка. В свободной генерации модель видела только задачу и данные. `data/` хранит полные отправленные тексты, сырые ответы, идентификаторы и учёт токенов. Анализаторы отвергают неполные матрицы, дубли, подменённые prompt, смешение моделей и некорректный JSON.

Python-эталоны получены исполнением выражений, арифметика проверена отдельно, а HTTP-эталоны сверены с [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html), разделами 15.3.5, 15.4.5, 15.5.2, 15.5.4, 15.5.5 и 15.6.4. Числа из академических работ не используются как результаты этой модели.

## Повторить с другой моделью

Живые клиенты `examples/run_live.py` и `stress/run_*.py` отделены от офлайн-проверок. Они читают `JUDGE_API_URL`, `JUDGE_API_KEY`, `JUDGE_MODEL` и при необходимости `JUDGE_CA_BUNDLE` из окружения и пишут новый JSONL-файл. Не включайте ключ в аргументы, исходники или журнал. Для сложной матрицы дополнительно требуются явный бюджет `JUDGE_V2_APPROVED_BUDGET_USD` и тарифы `JUDGE_V2_INPUT_USD_PER_M`, `JUDGE_V2_OUTPUT_USD_PER_M`; встроенная оценка по опубликованной цене не определяет счёт посредника.

```bash
python examples/run_live.py --output my-run.jsonl
python -I examples/eval_harness.py --analyze-recorded my-run.jsonl
```

Создавайте отдельный файл для каждого запуска. Клиент не перезаписывает существующий файл и не повторяет неопределённые сетевые исходы автоматически. Неверный формат, отказ, таймаут и ошибка API остаются отдельными категориями. Перед передачей собственного журнала другим людям проверьте запросы и ответы на секреты и личные данные.

Все 42 задания выбраны для проверки конкретных механизмов, а не как случайная выборка рабочего потока. Восемь предъявлений одной задачи связаны друг с другом; считать 336 вызовов независимыми задачами нельзя. Группы различаются задачами и рубрикой, поэтому их результаты не измеряют чистый эффект сложности. Нулевой результат не гарантирует отсутствие ошибок на иных темах, версиях модели или инструкциях.
